# RAG 检索评估

## 这是什么

`rag_eval_cases.json` 是检索链路的**回归基线**：每条用例给出一个真实风格的查询，以及期望在检索结果中出现的词。跑 `scripts/evaluate_rag_retrieval.py` 会把当前链路（Query Rewrite → 向量召回 → 精排）跑一遍，输出指标。

## 用例格式

```json
{"id": "xian-1", "city": "西安", "category": "景点",
 "query": "西安有哪些必去的景点，第一次去玩几天合适？",
 "expected_terms": ["兵马俑", "城墙", "大雁塔"]}
```

- `id` 唯一，命名 `{city}-{序号}`
- `city` 决定检索时的元数据过滤范围（必须与 `rag/guide_catalog.py` 的沉淀城市一致）
- `category` ∈ 景点 / 美食 / 行程
- `expected_terms` 是**子串**匹配：任一词出现在结果的 `content` 里即算命中。请只写攻略原文里真实出现的词（景点名、菜名）

当前规模：**48 条** = 6 城 × 8 条（景点 3 / 美食 3 / 行程 2）。

## 指标口径

| 指标 | 含义 | 期望 |
|---|---|---|
| Top1 Hit | 第 1 条结果命中任一期望词 | 越高越好 |
| Top3 Hit | 前 3 条中命中 | 越高越好，通常接近 1 |
| MRR | 首个命中结果的 `1/排名`，全未命中记 0 | 越高越好 |
| Noise Rate | 不含任何期望词的结果占比（垃圾比例） | 越低越好 |
| Latency | 完整链路平均耗时（关闭缓存） | 参考值，受网络影响大 |
| Cross-dest. Pollution | 结果中城市 ≠ 目标城市的占比 | **应≈0**，不为 0 说明元数据过滤或 adcode 判定有问题 |

## 怎么跑

```bash
# 全量（48 条，较慢：每条都要调一次改写 + 精排）
.venv\Scripts\python.exe -X utf8 backend/scripts/evaluate_rag_retrieval.py

# 快速验证前 3 条
.venv\Scripts\python.exe -X utf8 backend/scripts/evaluate_rag_retrieval.py --limit 3
```

## 改动检索链路时请对比前后

任何影响检索/精排的改动（换嵌入模型、改切片、调 `RAG_TOP_K`、启用/关闭 `RERANK_MODEL`）都应跑一次全量并对比：

- **启用精排**：在 `backend/.env` 设 `RERANK_MODEL=qwen3-rerank` 前后各跑一次，MRR 与 Noise Rate 应有改善
- **对照实验**：`RERANK_MODEL=` 留空则退回 LLM 打分，再留空且 LLM 不可用则退回规则打分

## 实测基线（2026-10-05，48 条全量）

同一份用例、同一份语料，仅切换精排方式：

| 指标 | 启用 `RERANK_MODEL=qwen3-rerank` | 关闭（退回 LLM 打分） |
|---|---|---|
| Top1 Hit Rate | 100.0% | 100.0% |
| Top3 Hit Rate | 100.0% | 100.0% |
| MRR | 1.000 | 1.000 |
| **Noise Rate** | **24.2%** | **14.6%** |
| **Avg Latency** | **1661 ms** | **5647 ms** |
| Cross-dest Pollution | 0.00% | 0.00% |

**怎么读这组数据**（重要，别误读）：

1. **Top1/Top3/MRR 已经饱和**（全 100% / 1.000），说明当前用例集对这两个排序方案**没有区分度**——真正的检索失败场景（同义表达、跨城混淆、空召回）没被覆盖到。
2. **时延是明确收益**：专用 cross-encoder 一次网络往返，比让 LLM 读片段打分快 **3.4 倍**。
3. **Noise Rate 变差要谨慎解读**：该指标统计「返回片段里不含期望关键词的比例」，**本身偏向关键词匹配的方案**。LLM 打分时模型看着查询词逐个比对，天然更容易把含原词的片段排前；cross-encoder 判的是语义相关，可能把语义更贴切但用词不同的片段排上来，反而被判为「噪声」。所以 24.2% vs 14.6% **不能简单读成质量下降**，更可能是指标口径的偏差。
4. 想真正比较两种精排，需要**人工标注相关性**或改用语义指标（如 RAGAS），当前的关键词口径做不到。

## 已知局限

- 只有**正向**用例（期望命中）。「应拒答 / 空召回」这类负向用例需要评估脚本支持新指标，当前未实现——评估脚本只统计命中，无法表达「不应该返回任何东西」
- `expected_terms` 是关键词式匹配，同义表达（用户说「省博」而攻略写「陕西历史博物馆」）算未命中，会低估真实效果
