## 一、项目概述

### 1.1 背景与问题

旅行规划是典型的高信息量任务：查景点、看天气、算预算、排行程、记偏好，全靠人手动跨多个网站完成，耗时且容易遗漏。市面上没有"一个对话就帮你排好三天行程"的轻量工具——这正是 Agent 的用武之地。

### 1.2 项目目标

构建一个**对话式智能旅行规划系统**：用户用自然语言说出"想去哪、玩几天、预算多少、什么偏好"，系统自动完成——收集需求 → 查实时信息 → 生成每日行程 → 估算预算 → 记住用户偏好，最终输出一份可直接使用的行程单。

### 1.3 价值点（为什么值得做）

- **完整串起所学知识**：LLM 接入（第3章）、ReAct 范式（第4章）、工具系统（第7章）、记忆（第8章）、上下文构建（第9章）全部用到
- **可运行可演示**：命令行交互，真实调用 deepseek + 搜索，效果直观
- **对初学者友好**：架构简单清晰，每部分都能看懂、能单独测试

## 二、技术选型

| 部分 | 选型 | 理由 |
|---|---|---|
| LLM | deepseek-flash（V4.1-Flash，已配 key） | OpenAI 兼容、便宜快速，**原生多模态（图像理解）**，支持 JPEG/PNG/GIF/WebP |
| 框架 | hello_agents v0.2.8（已装） | 教材框架：Agent 基类 + ToolRegistry + MemoryManager 直接用 |
| 搜索 | Tavily（已配 key） | 实时查天气、交通、景点信息的工具 |
| 记忆 | MemoryManager（框架自带） | 存用户偏好（情景记忆）+ 行程草稿（工作记忆） |
| 预算计算 | Calculator 工具（框架内置） | 精确算住宿/交通/门票合计 |
| 输出 | Markdown 行程单 | 结构化、可保存、可二次编辑 |
| 界面 | 命令行交互 | 第一版不做网页，专注核心逻辑 |

**设计原则**：第一版**代码自建、框架复用**——核心 agent 逻辑自己写（用教材第4章学的 ReAct 思路），基础设施（LLM 客户端、工具注册表、记忆管理）用框架包，避免重复造轮子。

## 三、功能设计

### 3.1 核心功能（MVP，第一版必做）

1. **需求收集**：对话式收集五个要素——目的地、天数、预算、同行人（亲子/情侣/独行）、偏好（美食/自然/人文/休闲）
2. **实时信息查询**：通过搜索工具获取当地天气、热门景点、特色美食、交通建议
3. **行程生成**：按天生成行程（上午/下午/晚上三时段），每天配景点+餐饮+交通建议
4. **预算估算**：住宿 + 市内交通 + 门票 + 餐饮 分项估算并合计
5. **偏好记忆**：记住用户历史偏好（下次规划自动带出，如"上次说喜欢人文"）
6. **行程单输出**：生成 Markdown 格式完整行程单，标注信息来源
7. **图片识别（多模态）**：用户上传照片 → deepseek-flash 视觉理解（识别景点/场景/需求）→ 纳入规划
8. **图片展示**：前端回显用户上传图 + 高德景点图片（POI 图片接口）在行程中展示

### 3.2 进阶功能（第二版，可选）

- 多目的地对比推荐（让 LLM 先推荐再规划）
- 行程导出 PDF / 分享文本
- 途中实时调整（"第二天太累了，改成轻松点"）

### 3.3 明确不做（第一版边界）

- 不做真实地图/导航（Agent 场景不必要，且组件受限）
- 不做真实订票（只做信息与规划，不接支付/预订）
- 不做多用户账号体系（单机单用户）

**双存储分工**：
- **SQLite（长期业务数据）**：`db_models.py` 定义 TripRecord 表（trip_id/destination/summary/itinerary_json/created_at/updated_at），`storage_service.py` 实现历史列表、详情、删除、导出支撑。理由：旅行方案是用户主动保存、需长期保留的业务数据，SQLite 适合个人项目与 Demo。
- **Redis（短期高频缓存）**：`cache_service.py` 统一 `trip_planner` 前缀 + JSON 序列化 + TTL 过期，被 weather/map/retriever 复用，缓存天气、地理编码/POI/路线、RAG 检索与重排序结果。理由：这些结果重复查询多、短期稳定，缓存可减少外部调用与检索开销。

## 七、核心实现要点（讲原理）

### 7.1 Agent 循环（教材第4章 ReAct 复用）

每轮让 LLM 输出 `Thought:` + `Action:`，程序正则解析：
- 工具调用：`Search[西安 3月 天气]` → 执行搜索 → 结果当 Observation 塞回历史
- 收尾：`Finish[完整行程单]` → 输出最终结果
- 上限 10 步防死循环

### 7.2 提示词三件套（教材第9章上下文工程思路）

1. **需求收集提示词**：让 LLM 输出结构化 JSON（目的地/天数/预算/同行人/偏好），缺啥问啥
2. **行程生成提示词**：输入"需求 + 搜索到的实时信息 + 历史偏好"，按天生成行程
3. **预算提示词**：输入行程，分项估算并合计（计算器工具兜底校验）

### 7.3 记忆设计（教材第8章）

- 用户说出偏好（"我喜欢人文景点"）→ 存入**情景记忆**（memory 工具）
- 下次规划时检索历史偏好，拼进提示词——"系统记得你"
- 第一版用框架 MemoryManager，不引入向量库，降低复杂度

### 7.4 多模态设计（deepseek-flash 原生支持）

- 用户上传图片（前端 File 上传）→ FastAPI 接收（存本地/uploads，转 base64 或生成访问 URL）
- 调用格式（OpenAI 兼容，LangChain HumanMessage 直接支持）：
  ```json
  {"role": "user", "content": [
    {"type": "text", "text": "这是我在大理拍的照片，推荐类似景点"},
    {"type": "image_url", "image_url": {"url": "data:image/jpeg;base64,xxx"}}
  ]}
  ```
- 识别结果（景点/风格/需求）注入行程生成的上下文
- 前端回显：上传图立即展示在对话区；行程中每个景点附高德 POI 图片 URL 展示

### 7.5 安全与容错

- 所有 LLM 输出用 `json.loads`/`ast.literal_eval` 安全解析，失败重试一次
- 搜索失败降级：用模型自身知识回答并标注"未验证"
- 工具执行异常返回错误文本而非崩溃（教材第4章 tools.py 的约定）

## 八、测试与验收

### 8.1 三个验收用例

1. **基础用例**：`帮我规划西安3天旅行，预算2000，带小孩` → 输出 3 天行程 + 分项预算 + 来源引用
2. **记忆用例**：先规划一次并声明"喜欢人文"，再规划北京 → 北京行程自动包含人文类景点
3. **容错用例**：输入不完整（只说"想去成都"）→ 系统主动追问天数/预算/偏好，不报错

### 8.2 质量检查

- 每个工具独立测试（tests/test_agent.py）
- 行程单字段完整（天数/时段/景点/餐饮/预算/来源）
- 预算分项合计正确（计算器复核）
- 报错信息人类可读，不抛裸异常

## 九、风险与备选

| 风险 | 影响 | 备选方案 |
|---|---|---|
| 搜索 API 限额 | 实时信息查不到 | 降级为模型知识回答，标注"建议核实" |
| LLM 输出格式不稳定 | 解析失败 | 提示词加强制格式 + 重试一次 + 降级重问 |
| 预算估算不准 | 用户质疑 | 用计算器工具显式分步计算，标注"估算" |
| 行程内容幻觉（编造景点） | 误导用户 | 提示词要求只基于搜索结果，来源引用标注 |
